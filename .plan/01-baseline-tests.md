# 01 — Baseline: real test suite + CI wiring

**Depends on:** none. Every other section depends on this one.

Read `.plan/CODEBASE.md`, `CLAUDE.md` (repo root) and `deploy/README.md` before starting.
There is currently **no test suite** — CI is compose-up + curl smoke checks. This section
adds the harness every later section will build on. **No refactoring, no feature code.**

## Goal

A pytest suite (api + database adapter) and a Playwright suite that run against the
compose stack, with a fake SMTP sink and a stubbed `union`, wired into CI as jobs that
must pass before images are built.

## Owns

- `tests/` (new tree — later sections each own their own subdirectory under it, see below)
- `docker-compose.test.yml` (or a test override/include file — new)
- `.github/workflows/deploy.yml` (add jobs; keep existing `test` smoke and `manifests` jobs green)
- `.plan/CODEBASE.md` (record the exact commands once they exist)
- `.gitignore` (add anything missing from: `session.json`, `*passkey*.json`, `.env*`,
  `*.har`, `.venv/`, `node_modules`, `.DS_Store` — most are already covered; add the rest)
- new dev-dependency pins (`backend/api/requirements*.txt`, `frontend/package.json` devDeps,
  `frontend/playwright.config.*`)

**Does not own** any existing application source file. If a test cannot be written
without changing application code, stop and report it rather than refactoring.

## Test stack design

- A separate compose project (e.g. `docker compose -f docker-compose.yml -f
  docker-compose.test.yml -p eesoc-test`) so the dev stack is untouched. The override:
  - runs **mailpit** (or an in-process SMTP capture) and points `SMTP_HOST`/`PUB_SMTP_*`
    at it;
  - forces `ENVIRONMENT=development`, `DEV_LOGIN_ENABLED=true` — dev login is the only
    auth path in tests;
  - replaces `union` with a fixture-serving stub (a tiny FastAPI app in `tests/` returning
    canned eActivities responses; no real Union calls ever, in tests or CI);
  - pins a fresh postgres volume per run.
- pytest lives on the host venv or a container — whichever is reliable in CI; API tests
  talk to `http://localhost:8080/api` through nginx exactly as a browser would.
- Playwright runs against the same stack. Give it a storage-state bootstrap that signs in
  via dev login. Keep to **key flows only**: home renders, events list + event page,
  sign-in via code (code read from mailpit or the api logs), one admin page loads.

## Conventions for later sections (write these into tests/README.md)

- Each later section owns exactly `tests/<slug>/…` for pytest and
  `tests/e2e/<slug>/…` (or clearly prefixed spec files) for Playwright. CI discovers the
  whole `tests/` tree, so **no section after this one edits the workflow to add tests.**
- Tests must never read `.env` or `backend.env` (CI copies the `.example` files).
- Only this section and section 02 may edit `.github/workflows/deploy.yml`; others add
  test files only.

## Acceptance criteria (all must pass in CI)

1. `pytest` job: runs the api+database suites against the compose test stack, green,
   including at least: health, migrations applied, dev login refused when
   `DEV_LOGIN_ENABLED` is false, one events list/detail read, one write path through
   dev-login auth (e.g. create+delete a test resource as admin).
2. Playwright job: the key flows above pass against the same stack.
3. Mail assertions work: a login code email is visible in the mailpit sink from a test.
4. The stub `union` serves fixtures; a test asserts the api can render events with union
   data present, and CI makes **zero** network calls to real ICU hosts (no `ICU_API_KEY`
   anywhere in the test env).
5. The existing `test` (smoke) and `manifests` jobs still pass unchanged.
6. `docker compose down` then `up` on the dev stack still works as documented (the
   override must not break normal dev usage).
7. `.gitignore` covers the required list; nothing generated by the test run (volumes,
   screenshots, traces) is committable by accident.

## Constraints to pass to the implementer

- Never read or print `.env`, `backend.env`, or any secret.
- Nothing environment-specific in `deploy/k8s/base/`; do not touch `deploy/` in this
  section at all.
- Commit messages `area: what changed`. Record commands in `.plan/CODEBASE.md`.
